# 评价理论：结构复杂度与理解难度

本库把“结构本身的复杂程度”和“人理解这种结构的难度”作为两个独立的维度。

> 初稿。标“报告”的说法来自 2026-10 调研报告；标“整理者推演”的是由此推出的，没有经过验证。

## 两个维度各是什么

| 维度 | 属于谁 | 问的是 |
| --- | --- | --- |
| 结构复杂度 | 被表达的对象（系统、知识、认知），与怎么画无关 | 对象里有多少成分、多少种关系、几层嵌套，跨层联系多不多，有没有环、反馈和随时间的变化 |
| 理解难度 | 人、任务和表示方式三者的组合 | 某个人用某种表示方式完成某个任务有多难 |

结构复杂度是对象的性质，换一种画法它不会变。理解难度不是对象的性质：同一个结构，换表示方式、换任务、换使用者，难度都会变。

## 为什么要分开

- 复杂的结构未必需要复杂的图形。一个恰当的抽象、矩阵或分层文章，有时比高度复杂的三维交互系统更容易传达认知。（报告）
- 表面简单的结构，其中的动态、因果和多层关系也可能很难被人真正理解。（报告）
- 如果合成一个“复杂度”，容易出现两种误判：把“图画得复杂”当成“表达得好”，把“结构复杂”当成“必须用复杂图形”。（整理者推演）

这个区别决定了本库怎么评价每一种可视化范式：不给“复杂度总分”，而是在固定结构复杂度的前提下，比较不同表示方式把理解难度降到了什么程度。

## 两个维度的组合（示意）

下表是示意，不是分类标准。

| | 理解难度低 | 理解难度高 |
| --- | --- | --- |
| **结构复杂度低** | 小而直接的结构，配合合适的图形 | 结构看似简单，但含动态、因果或多层关系；或表示方式选得不合适 |
| **结构复杂度高** | 有好的抽象、分层或合适的表示（如矩阵、分层文章） | 结构复杂，表示方式又没有帮到理解（如密集网络画成节点连线图） |

（整理者推演）

## 对评价的含义

1. **固定结构，再比较表示。** 比较两种表示方式，要在同一个结构、同一个任务下进行。[可复现的测试场景](../03-project-reviews/reproducible-tests.md)就是这样设计的：测试材料固定结构复杂度，观察到的是理解难度。
2. **难度只对任务有意义。** 先明确领域问题和用户任务，再谈难度。这是 Munzner 的方法（见[经典研究](references.md)）。
3. **区分“降低了难度”和“增加了操作成本”。** 三维、折叠、多视图这类手段，要看它们降低的是结构复杂度带来的理解难度，还是只增加了空间操作成本。（报告提出的问题）
4. **抽象有代价。** 压缩表达之后，哪些信息被保留、哪些被扭曲，也是难度的一部分。见[抽象层级与颗粒度](../04-structure-and-cognition/abstraction-and-granularity.md)。

## 怎么描述结构复杂度（候选，待定）

报告没有给出指标。它的测试一用下面这些参数设定了一个复杂的测试系统，这里把它们整理成成分清单，不给公式。

| 成分 | 说明 |
| --- | --- |
| 规模 | 节点和关系的数量 |
| 关系种类 | 不同含义的连接有几种 |
| 嵌套深度 | 父子层级有几层 |
| 跨边界连接 | 跨子系统、跨层的连接有多少 |
| 环与枢纽 | 循环依赖、高连接度节点 |
| 动态 | 结构是否随时间变化，有无反馈 |
| 多重结构 | 同一对象是否同时具有组织、依赖、任务、事件、时间等多种独立结构（报告：不能只靠一棵层级树表达） |

## 怎么描述理解难度（候选，待定）

难度只能相对一个任务和一类使用者来说。下面是报告的五个测试里出现的可观察方面：

- 折叠、展开之后，用户能否持续跟踪同一个对象。
- 对象跨视图是否保持稳定身份，能否准确定位到对应对象。
- 能否把静态组织、任务路由、动态执行和微观调用连接起来。
- 能否回溯到原始判断，能否区分不同类型的概念关系。
- 加入新内容后，是否造成重要知识丢失。

## 待定

- 理解难度怎么测：任务完成时间和正确率，还是只做定性观察。
