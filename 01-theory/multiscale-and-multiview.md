# 多尺度与多视图

问题：同一个对象在不同尺度、不同视角之间切换时，怎样保持对象身份、语义和上下文。

> 初稿。标“报告”的说法来自 2026-10 调研报告；标“整理者推演”的是由此推出的，没有经过验证。

报告的判断是：很多项目分别做好了某一张图，但多视角与跨粒度的连续性值得作为独立的研究问题。

## 模型的层次与展示的层次

这是两回事。

- **模型的层次**：数据里有哪些结构。同一个系统可能同时有组织、依赖、任务、事件、时间等多种独立结构，不能只靠一棵层级树表达。（报告）
- **展示的层次**：当前这张图画到了哪一层、哪个粒度。

把两者混在一起，就会出现“换一种视角便要重新组织全部数据”的问题。（报告）

## 四个具体问题

### 1. 对象身份

同一个对象在不同视图里是不是同一个？筛选、高亮的状态能否跨视图保留？能否从一个视图进入另一个视图，并准确定位到对应对象？

例子：AgentEnsemble 把计划依赖 DAG 和实际执行时间图分成两张视图，值得研究同一个任务在两张图里的身份怎么保持一致，点击任务又如何进入工具调用或会话详情。见 [AgentEnsemble Viz](../catalog/INDEX.md)。

对应测试：[测试二](../03-project-reviews/reproducible-tests.md)。

### 2. 聚合与展开

折叠一个子系统后，原来连到子系统内部的跨模块边怎么合并，方向、数量和关系类型怎么保留，展开后怎么恢复，布局会不会剧烈跳动。见[交互范式](interaction-patterns.md)里“折叠不只是隐藏”一节。

对应测试：[测试一](../03-project-reviews/reproducible-tests.md)。

### 3. 静态结构、运行轨迹和聚合拓扑

三者是不同的数据，可能互相映射，但不是同一份。

| 结构 | 含义 |
| --- | --- |
| 静态依赖图 | 系统设计中可能发生什么调用 |
| 运行时 Trace | 某一次运行实际发生了什么 |
| 聚合服务拓扑 | 多次运行中观察到哪些服务之间存在调用 |

Nx 把 Project Graph（项目之间的依赖）和 Task Graph（实际构建任务）分开：模块之间存在依赖，不代表每次任务都会经过全部依赖路径。（报告）

对应测试：[测试三](../03-project-reviews/reproducible-tests.md)。

### 4. 模型与视图分离

一份结构模型生成多张不同视角的图，而不是每张图各自维护一份数据。LikeC4 和 Structurizr 是这一思路的代表。值得继续核实的是跨视图的对象定位和复杂模型的导航。（报告）

## 已知的功能空白

报告没有找到充分证据，表明任何单一项目已经完整实现多智能体的六种视角（全局协作、组织抽象、实际任务、业务逻辑、个体决策、微观执行）及其无损跨层切换。这是需要重点记录的空白，不应用抽象描述掩盖。详见 [L2 多智能体](../02-visualization-ecosystem/L2-specialized-visualizations/README.md)。

## 与结构复杂度、理解难度的关系

按[评价理论](evaluation-theory.md)的区分：多视图切换不会让对象本身变简单，结构复杂度不变；它的作用是把一个复杂结构分成几个较容易看的侧面，降低每次观察的理解难度。代价是跨视图的一致性和切换的操作成本。（整理者推演）

所以评价一个多视图系统，要同时看两件事：每个视图单独看是否容易理解，以及切换时有没有丢掉对象身份和上下文。
