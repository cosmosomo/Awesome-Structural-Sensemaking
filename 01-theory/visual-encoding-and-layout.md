# 视觉编码与布局

问题：位置、形状、颜色、大小和连线怎样承载含义；布局决定对象摆在哪里，又怎样影响人理解结构的难度。

> 初稿，材料有限。通用的视觉编码理论没有在这里展开，直接借用 Munzner 的方法（见[经典研究](references.md)）：数据抽象和视觉设计分开做。这里只记录与“结构”直接相关的几个问题。标“报告”的来自 2026-10 调研报告，标“官方文档”的是核对过的页面，标“整理者推演”的没有经过验证。

## 视觉编码在结构图里承载什么

下表是整理者的归纳，没有经过验证。

| 视觉元素 | 常见用法 | 要问的问题 |
| --- | --- | --- |
| 位置 | 层级、先后、聚类、时间轴 | 位置有没有语义？力导向布局里位置只是计算结果，不能当成含义 |
| 连线 | 关系、方向、调用 | 一条线表示一个关系还是一批关系？聚合边要保留方向、数量和关系类型（报告） |
| 形状与容器 | 对象类别、嵌套归属 | 嵌套是组成关系还是只是分组 |
| 颜色 | 状态、类别、强弱 | 颜色表示的是状态还是类别，能不能同时编码两件事（整理者推演） |
| 大小 | 规模、重要性 | 大小对应哪个可度量的属性 |

“颜色表示状态”“力导向”“层次布局”是报告里举的视觉编码和布局的例子。

## 布局的几种家族

按报告对各引擎用途的描述整理：

| 布局家族 | 适合 | 条目 |
| --- | --- | --- |
| 分层布局 | 有方向的结构：工作流、依赖图、任务 DAG | ELK.js、Dagre、Graphviz |
| 力导向布局 | 没有明确方向的关系网络；动态关系图；大规模网络用 GPU 加速 | d3-force、Cosmos.gl |
| 复合图布局 | 带父子嵌套的复杂模块 | ELK.js（报告：复合图布局）、Cytoscape 的复杂度管理扩展 |

条目详情见 [L1 布局与复杂度管理算法](../02-visualization-ecosystem/L1-foundational-technologies/README.md)。

## 聚合与布局是两件事

结构聚合算法决定显示哪些对象、合并哪些关系；视觉布局算法决定这些对象显示在哪里。（报告）

聚合在界面上常表现为一个可展开的“合成节点”。Nx 的项目图就是这样：合成节点代表同一文件夹下的一组项目，可以就地展开，也可以聚焦，只显示节点内部的项目；官方文档说合成节点对浏览哪怕中等规模的图都是必要的（官方文档，nx.dev，2026-10-13 访问）。这说明聚合不只是为了省空间，它本身就是导航手段。

## 布局稳定性

折叠或展开之后，节点位置是否剧烈跳动，决定了用户能不能持续跟踪同一个对象。这是报告测试一的观察项之一，见[可复现的测试场景](../03-project-reviews/reproducible-tests.md)。它也属于[多尺度与多视图](multiscale-and-multiview.md)里“聚合与展开”的问题。

## 降维与三维

高维结构投影到二维或三维之后，位置来自降维计算，不应理解为原始空间里的真实坐标。这一类问题（降维之后哪些信息被保留、哪些被扭曲；视图太多时谁来挑；再加一个空间维度有没有帮助）已经单独成篇，从案例归纳：见[高维可视化](high-dimensional.md)。报告还提出的第三个问题——三维交互是真正降低理解成本，还是只增加空间操作成本——在那里有文献的实证旁证（交互式三维散点图“很少有帮助、常常更差”）。

## 待研究

1. 同一个结构，换不同的布局算法，用户持续跟踪一个对象的难度怎么变？按[评价理论](evaluation-theory.md)的做法，固定结构、固定任务，比较布局。
2. 聚合边怎样同时显示数量、方向和类型，又不让图变得更难读？
3. 视觉编码里，哪些承载的是结构本身的含义，哪些只是布局计算的副产品，怎样让读者分得清？
4. 跨视图切换时，同一个对象的位置、颜色是否要保持一致，保持到什么程度？
